# DOCUMENTATION_RULES

Project documentation exists to preserve relevant decisions, contracts, patterns, and constraints.

## When to Create Documentation
- When a component has a defined contract or usage rules

- When a reusable pattern emerges across multiple contexts

- When a non-obvious decision is made

- When a known limitation or trade-off is accepted

## When NOT to Create Documentation
- For obvious or self-explanatory code

- For trivial wrappers with no meaningful behavior

- For temporary decisions still under discussion

- For features or implementations that do not introduce new patterns or constraints

## Principles
- Document decisions, not implementation details

- Keep documentation short, clear, and objective

- Ensure documentation reflects the current state of the project

- Avoid unnecessary or redundant documentation

## Consistency Rule
- Documentation must always stay aligned with the codebase and actual behavior

- If documentation becomes outdated, it MUST be updated or removed
